# WI-3: Role-aware implement-app state, gates, and protocol

## Outcome

`implement-app` supports tester and developer roles with role-specific
completion gates that incorporate compile and test outcomes, driven by
skill-derived completion requirements.

## Context

The current `ImplementApplication` has hardcoded completion gates: inspect →
mutate → verify (content_id match) → ready → summary. There is no compile or
test state. To serve as a tester (write a test, verify it compiles and runs
red) or developer (write implementation, verify it compiles and test runs
green), the application needs role-specific gates that check compile and test
outcomes.

This work item depends on WI-1 (process execution tools) and WI-2 (kernel-level
skill system with completion requirements).

## Key design decisions

- **Request protocol extension.** `ImplementRequest` gains `role`
  (`Tester | Developer`), `compile_command` (`Vec<String>`), and `test_command`
  (`Vec<String>`). These are optional for backward compatibility but required
  when role is specified. Protocol version bump to `implement.request/v1`.
- **State extension.** `ImplementState` gains `compiled`, `compile_failed`, and
  `test_result: Option<TestOutcome>` (`Passed | Failed | NotRun`). Tracked in
  `reduce_event` by observing `run_check` and `run_test` tool-completed events.
- **Completion gates by role.** Shared gates (no mutation before inspection,
  target inspected, mutation applied, ready, summary) are unchanged. Role-specific
  gates: tester requires `compiled == true` and `test_result == Failed` (red);
  developer requires `compiled == true` and `test_result == Passed` (green).
  The existing `verified` gate (content_id match) is retained for both roles.
- **Result extension.** `ImplementResult` gains `compiled`, `test_result`, and
  `role` fields. Protocol version bump to `implement.result/v1`.
- **System instructions by role.** Tester: "write a test that fails (red)
  because the implementation does not exist yet. After writing, run_check then
  run_test. Complete only when the test compiles and runs red." Developer:
  "write the implementation. After writing, run_check then run_test. Complete
  only when the project compiles and the test passes (green)."
- **Tool registration is conditional.** `run_check` and `run_test` are only
  registered when the request carries the corresponding commands. A request
  without a role gets the current 3-tool catalog.
- **Built-in skills.** `implement-tester` (completion requirements:
  `["inspected", "mutated", "compiled", "test_red"]`) and `implement-developer`
  (completion requirements: `["inspected", "mutated", "compiled", "test_green"]`).
  Registered in `BuiltinSkillRegistry` from WI-2.

## Affected files

- `crates/implement-app/src/lib.rs` — extended request, state, gates, result,
  instructions, tool registration, skill resolution
- `crates/implement-cli/src/main.rs` — new CLI flags, request construction
- `crates/implement-cli/tests/` — new integration tests for role-based flows

## Acceptance Criteria

- [ ] `ImplementRequest` with `role: Tester` and compile/test commands produces a result where `compiled == true` and `test_result == "failed"` when the test correctly runs red
- [ ] `ImplementRequest` with `role: Developer` and compile/test commands produces a result where `compiled == true` and `test_result == "passed"` when the implementation makes the test pass
- [ ] Completion is rejected (remediable) when the tester's test passes green instead of failing red
- [ ] Completion is rejected (remediable) when the developer's test fails red instead of passing green
- [ ] Completion is rejected (remediable) when `run_check` has not been called or returned a non-zero exit code
- [ ] A request without a role and without compile/test commands produces identical behavior to the current implement-cli (backward compatibility)
- [ ] `ImplementResult` includes `compiled`, `test_result`, and `role` fields
- [ ] The tester and developer skills are resolved from the `BuiltinSkillRegistry` and their completion requirements are checked in `validate_completion`
- [ ] Exit codes for role-based results follow the existing contract (0 = candidate ready, 3 = indeterminate)
