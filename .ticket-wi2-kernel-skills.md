# WI-2: Kernel-level skill types and registry

## Outcome

Skill types move from `review-app` into a shared location in `agent-kernel` so
both `review-app` and `implement-app` can use them. Skills gain the ability to
carry completion requirements as data that applications interpret in
`validate_completion`.

## Context

The current `skills.rs` lives in `review-app` as an inline module. It has
`Skill` structs with content hashes and applicability globs, but skills only
inject instruction blocks — they do not affect completion validation.
`agent-kernel` has zero skill awareness. The `AgentApplication` trait and
`ApplicationInitialization` struct have no skill fields.

For implement-cli role support, skills need to carry role-specific instructions
**and** completion requirements (e.g. "test must run red" for the tester role)
that the application interprets in `validate_completion`.

This corresponds to the skill system element of Vertical 5 from the platform
plan, generalized from Review-specific to kernel-level.

## Key design decisions

- **Skill types in `agent-kernel`.** Move the `Skill` struct (id, version,
  content_hash, instruction, applicability, required) from `review-app` into
  `agent-kernel`. Add a `CompletionRequirement` type that skills can carry —
  a declarative description of what the application must verify before
  accepting completion.
- **Skill registry trait.** A `SkillRegistry` trait in `agent-kernel` that
  resolves skills for a given application and set of signals (e.g. changed
  file paths). The built-in registry holds hardcoded trusted skills.
- **Skills remain permission-neutral.** Per the design spec (§5.8): skills
  provide instructions, recommended tools, schemas, and completion
  requirements. Skills **cannot** add capabilities, register tools, or
  override system policy. The `CompletionRequirement` data is interpreted by
  the application's `validate_completion`.
- **ApplicationInitialization gains skill fields.** Add `requested_skills` and
  `resolved_skills` to `ApplicationInitialization`. The coordinator resolves
  skills during initialization. This aligns with design spec §9.3.
- **No external skill loading yet.** Built-in trusted registry only.
  File-based or repository-local skill loading is deferred.
- **review-app refactor is mechanical.** No behavior change for Review.

## Affected files

- `crates/agent-kernel/src/skills.rs` (new) — `Skill`, `CompletionRequirement`,
  `SkillRegistry` trait, `BuiltinSkillRegistry`
- `crates/agent-kernel/src/lib.rs` — export skills module
- `crates/agent-kernel/src/application.rs` — add skill fields to
  `ApplicationInitialization`
- `crates/agent-kernel/src/coordinator.rs` — resolve skills during
  initialization, pass to application
- `crates/review-app/src/skills.rs` — remove or reduce to a thin adapter
- `crates/review-app/src/lib.rs` — use kernel-level skill registry
- `crates/implement-app/src/lib.rs` — use kernel-level skill registry

## Acceptance Criteria

- [ ] `Skill` and `CompletionRequirement` types exist in `agent-kernel`
- [ ] `BuiltinSkillRegistry` resolves skills by applicability signals
- [ ] `ApplicationInitialization` carries resolved skills
- [ ] `review-app` produces identical review results before and after the refactor (golden test regression)
- [ ] `agent-kernel` has no dependency on `review-app` or `implement-app`
- [ ] A skill's `CompletionRequirement` is accessible to the application's `validate_completion` method
- [ ] Skills cannot register tools or expand capabilities (verified by test: a skill's tool recommendations are intersected with the catalog, not added to it)

## Dependencies

None directly, but should be done before WI-3 since WI-3 consumes the skill system.
