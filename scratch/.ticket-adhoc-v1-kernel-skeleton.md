# V1 — Kernel coordinator, scripted provider, and typed tool loop

Introduce the `agent-kernel` crate with the `AgentApplication` contract, a sequential session coordinator, a scripted model provider, typed tool adapter, and in-memory event ledger. A minimal fake application with a different completion schema proves the kernel is application-agnostic. This vertical proves the application/kernel seam without real model tokens or git.

## Acceptance Criteria
- [ ] A sequential session coordinator runs a registered `AgentApplication` through the full loop — model request, action dispatch, tool execution, ledger append, completion — without any application-specific conditional branching, proven by running a minimal fake application with a different completion schema through the same coordinator code path.
- [ ] A scripted model provider returns a fixture-defined sequence of model responses that drive the coordinator through at least one tool call followed by a completion request.
- [ ] Every tool call produces an execution receipt in the in-memory ledger containing session, turn, action, and execution identifiers per kernel spec §13.3.
- [ ] A model action referencing a tool absent from the effective catalog is rejected with a typed `kernel.action_rejected` event and no tool handler is invoked.
- [ ] A model action whose tool arguments fail strict JSON schema validation does not invoke the tool handler and produces a typed validation error event.
- [ ] A remediable completion rejection consumes a completion-attempt budget and does not reset any other cumulative counter (turns, tool calls, model attempts).

### Context
- Depends on V0 workspace and `agent-protocol` crate existing.
- Creates new crate `agent-kernel` per vertical plan §3 and V1 work item 1.
- `AgentApplication` trait with associated types for request, state, action, completion, result, and error — per kernel spec §9.1. In Rust this is a trait with associated types; the methods are `validate_request`, `initialize`, `build_system_instructions`, `build_context`, `reduce_event`, `parse_application_action`, `handle_application_action`, `parse_pause`, `validate_pause`, `parse_completion`, `validate_completion`, `build_terminal_result`.
- `ApplicationDescriptor` (application_id, application_version, request_schema, completion_schema, result_schema, domain_event_namespace) per kernel spec §9.2.
- `ApplicationInitialization` (initial_state, requested_tools, requested_capabilities, requested_skills, mandatory_skills, application_limits, immutable_metadata) per kernel spec §9.3.
- Event reduction is a pure reducer — no I/O, no model calls, no clock reads (kernel spec §9.4).
- Applications that don't support `application_action` or `pause_request` must provide parsers that reject those action kinds with a typed validation error (kernel spec §9.5).
- Coordinator pseudocode is in kernel spec §8.5; the Rust implementation must append the relevant ledger event before each state transition.
- `CanonicalModelRequest` / `CanonicalModelResponse` per kernel spec §11.2–11.3; `ModelProvider` trait per §11.1.
- `ScriptedModelProvider` is a test-only deterministic provider whose response sequence is fixture data (V1 work item 2). It implements `ModelProvider` and returns responses in order.
- Model action union: `tool_call`, `completion_request`, `pause_request`, `application_action` per kernel spec §12.1; MVP processes actions sequentially in response order per §12.2.
- `ToolDefinition` (name, version, description, input_schema, output_schema, required_capabilities, side_effect, idempotency, parallel_safe, cache_policy, max_calls_per_session, default_timeout_seconds, handler) per kernel spec §13.1.
- `Tool` (typed) and `DynTool` (type-erased adapter) with strict JSON input/output validation per V1 work item 3 and kernel spec §13.4–13.5. Input validation rejects unknown fields; output validation normalizes exceptions into `ToolError`, applies limits, redacts, validates schema, computes content hash.
- `ToolResult` (status: succeeded/failed/denied/cancelled/timed_out, value, error, content_hash, truncated, redactions, domain_events) per kernel spec §13.2.
- In-memory `LedgerStore` per kernel spec §16.4; event envelope (schema_version, session_id, sequence, event_id, occurred_at, type, producer, causation_id, correlation_id, payload_schema, payload, integrity) per §16.1; kernel event types per §16.2.
- `CompletionDecision` variants: `CompletionAccepted`, `CompletionRejectedRemediable` (reason_codes, missing_requirements, feedback_for_model), `CompletionRejectedTerminal`, `CompletionPaused` per kernel spec §18.2.
- Rejection semantics per kernel spec §18.3: rejection appends an event before another turn, consumes a completion-attempt budget, cannot increase any other budget, feedback identifies observable missing work.
- The fake application (V1 work item 7) has a different completion schema — e.g., a trivial "echo" app that accepts completion after any single tool call — to prove the coordinator has no Review-specific logic.
- Minimal context builder with authority-labelled `ContextBlock`s per kernel spec §17.1–17.2; V1 only needs system instructions + untrusted tool evidence labels.
