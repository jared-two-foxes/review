# V1 — Golden event and result fixtures for scripted scenarios

Add golden event and result fixtures for all four scripted V1 scenarios, verified by deterministic replay. This proves the end-to-end execution path is reproducible and that the same scripted actions reconstruct equivalent state.

## Acceptance Criteria
- [ ] Golden event fixtures for each scripted scenario match the actual in-memory ledger event sequence produced under a deterministic test clock and ID generator.
- [ ] Golden result fixtures for each scripted scenario match the actual review result output (verdict, status, and structured payload) under the same deterministic sources.
- [ ] Replaying an identical scripted response sequence with the same deterministic clock and ID source produces byte-identical ledger events and results to the checked-in golden fixtures.

### Context
- Depends on V1 kernel skeleton and Review application both being complete.
- Four scripted scenarios per V1 end-to-end scenarios (vertical plan §7):
  1. Script reads the change via `read_change` and completes with no findings → `APPROVED`.
  2. Script requests completion immediately → rejected as remediable, then reads the change and completes → `APPROVED`.
  3. Script references an unknown tool → typed invalid-action result (`kernel.action_rejected`).
  4. Script emits malformed tool arguments → handler is not invoked, typed validation error event.
- Golden fixtures are checked-in files, e.g. `tests/fixtures/v1/golden-events-{scenario}.json` and `tests/fixtures/v1/golden-result-{scenario}.json`.
- Determinism requires the test clock and ID generator interfaces from V0 to be injectable into the coordinator and ledger (vertical plan §6, §18.2 determinism policy).
- The V1 acceptance test "Replaying the same scripted actions reconstructs equivalent Review state" (vertical plan §7 acceptance tests) is satisfied by criterion 3.
- Per vertical plan §18.2: inputs and records must be reproducible even though model evaluations are probabilistic; V1 uses scripted providers so byte-identical replay is expected, not approximate.
- Scenarios 3 and 4 exercise kernel-level rejection paths, so their golden fixtures include the `kernel.action_rejected` / validation error events and the resulting `ReviewResult` with an indeterminate or error status, not a verdict.
