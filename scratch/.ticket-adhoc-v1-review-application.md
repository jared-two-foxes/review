# V1 — Review application state, completion gate, and verdict

Implement the minimal Review application that runs on the kernel coordinator: review state containing scope and inspected artifacts, an in-memory `read_change` fixture tool, a completion rule requiring inspection, and mechanical verdict calculation. Scripted scenarios produce `APPROVED` or `CHANGES_REQUESTED` results.

## Acceptance Criteria
- [ ] A scripted provider that calls the `read_change` fixture tool and then requests completion with no findings produces an `APPROVED` verdict through the kernel coordinator.
- [ ] A `completion_request` issued before the change has been inspected is rejected as remediable with structured missing requirements, and the session continues to a successful `APPROVED` completion after the model subsequently reads the change and re-requests completion.
- [ ] The effective tool catalog exposed to the model contains no mutation capability — no tool description, schema, or capability label implies write, command, network, or git-mutation authority.
- [ ] The session can terminate as completed only through a `completion_request` that the application's `validate_completion` accepts; no other action kind can produce a `completed` terminal state.
- [ ] Mechanical verdict calculation from normalized review state produces the changes-requested verdict when a blocking finding exists and the approved verdict when no blocking findings are present.

### Context
- Depends on V1 kernel skeleton (`agent-kernel` crate with `AgentApplication`, coordinator, scripted provider, tool adapter, ledger) being complete.
- Implements the Review application in the existing `review-app` crate (created in V0).
- Review `ApplicationDescriptor`: application_id `"review"`, application_version `"0.1.0"`, request_schema `"review.request/v1"`, completion_schema `"review.completion/v1"`, result_schema `"review.result/v1"`, domain_event_namespace `"review"` per kernel spec §9.2.
- Review state (minimal V1): scope, set of inspected artifacts (tool receipts from `read_change`), completion status, findings. Per V1 review capabilities.
- `read_change` is an in-memory fixture tool — not a real git tool — that returns a hardcoded change summary. It is the only tool in V1's Review catalog. Its `ToolDefinition` must declare `side_effect: "none"`, `required_capabilities` empty or read-only, no write/command/network labels.
- Completion rule: at least one `read_change` tool receipt must exist in review state before completion is accepted (V1 review capabilities + work item 6). If not, return `CompletionRejectedRemediable` with `missing_requirements` listing "change not inspected" and `feedback_for_model` blocks that identify the observable missing work without leaking hidden policy (vertical plan §2.4, kernel spec §18.3).
- Verdict policy: a blocking finding in the review state → `CHANGES_REQUESTED`; no blocking findings → `APPROVED` (V1 review capabilities). In V1, findings come from the completion payload (the model's structured output), not from evidence validation — that arrives in V3.
- The same coordinator that runs the fake application (kernel skeleton ticket) runs Review without any coordinator-level branching — both implement `AgentApplication` and the coordinator is generic.
- Review application must reject `application_action` and `pause_request` with typed validation errors since it doesn't support them in V1 (kernel spec §9.5).
- `build_terminal_result` maps terminal state + review state into the existing `ReviewResult` type from V0 (`review.result/v1`).
